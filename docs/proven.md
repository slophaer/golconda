This is the one place that says how far the work has got; the design pages say why. Each row is a
marker of `scripts/boot-test`, which runs the image in QEMU with OVMF; the flags are in
[Image artifacts: the boot test](reference/image.md#boot-test-scriptsboot-test). The image enforces
IPE, so every run of the default image uses `--secure-boot`; the last column lists the flags on top
of it. The image for a host without Secure Boot (`/system.secureBoot = false`,
`image-smoke-test-nosb`) runs without it, on OVMF with no Secure Boot and no TPM.

Runs at the same time: the default boot, `--next`, `--next --fail-health`, `--imds` and
`--next --tamper-index` booted one image together with `scripts/verify --boot-set`. Each used its
own ssh port and its own update or metadata server (the guest's `169.254.169.2:8074` on QEMU's
network `169.254.169.0/24`; for `--imds`, `169.254.169.254:80`), all five passed, and the run exited
with status 0. The PASS lists of the default boot and of `--next` are those of a run alone, plus
`imds-import-inactive`
([Image artifacts: the boot test](reference/image.md#boot-test-scriptsboot-test)).

`--imds --next` boots the faked Hetzner Cloud and then updates the image from the update server on
the same network: `imds-endpoint-locked` (only the endpoint `169.254.169.254` is locked) and
`http-fetch`, `sysupdate-installed`, `boots-next` and `no-failed-units-after-update` pass in one
run.

## `/imds` on Hetzner Cloud

On 2026-11-09 one `cpx12` in `fsn1` (UEFI, no Secure Boot, no TPM) booted the image of this branch
with `["/imds"]`, written from the rescue system, and no credential on the ESP. The user data listed
`ssh.authorized_keys.root`, a test credential and `network.network.60-hetzner-ipv6`: the server's
`<prefix>::1/64`, `Gateway=fe80::1`, `UseHostname=no` and the IMDS lock. Runs by hand, not boot-test
markers. The image had the first form of the fix: a udev rule for Hetzner's paths, and the lock only
in the user data. The branch now patches systemd's hwdb and keeps the lock on `lo`; that form has
run in QEMU only (`--imds`).

| claim                                                                                              | evidence                                                                                                                                                            |
| -------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| imdsd reads Hetzner's paths from `/imds`'s udev rule; the import passes; no unit failed            | `udevadm info`: `IMDS_DATA_URL=http://169.254.169.254/hetzner/v1`, no `IMDS_KEY_SSH_KEY`; `Imported 3 credentials from IMDS`; `systemctl --failed` empty            |
| the host name comes from the metadata                                                              | `hostname` and `/etc/hostname` are the server's name                                                                                                                |
| root's key comes from the user data; the project key that the metadata lists does not log in       | a login with the user data's key; `Permission denied (publickey)` for the project key                                                                               |
| the user data's `.network` file configures the link in the same boot; IPv6 works                   | `Installed /run/systemd/network/60-hetzner-ipv6.network from credential`; the link has `<prefix>::1`; `systemd-pull` fetched `https://ipv6.google.com/` (AAAA only) |
| with the lock in that file, only imdsd reaches the endpoint; a file without it lets any process in | `systemd-pull` of the endpoint: `Could not connect to server`; `systemd-imds -K hostname` answers; with a lock-less file, `systemd-pull` got the host name          |
| the same on the next boot                                                                          | the import, the second network generator run and the IPv6 address again; no failed unit                                                                             |

Not proven:

- **Enrolment on real firmware.** The harness enrols keys offline in the variable store.
- **Hardware.** Only QEMU with OVMF on x86_64 has run. aarch64 is postponed after v1
  ([Scope](design/scope.md)), because no aarch64 package can be built here.
- **Loader recovery by hand.** A loader that no longer starts, a lost ESP and a lost `db` key
  ([Boot loader: Recovery](design/bootloader.md#recovery)) have no marker. The rotation run has two
  releases, so it leaves out step 4 of the rotation.
- **A boot without the `db` enrolled.** It stops at switch-root; the harness has no marker for it.

One release was signed with a deployment key set that `scripts/make-keys` wrote outside the store.
It booted on the same markers as the throwaway set, and its next release installed over HTTP
([Release](reference/release.md)).
